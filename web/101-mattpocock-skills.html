slide 03 / 13 為什麼不能只靠 prompt為何不能只靠直覺指令 核心洞察問題不在模型

快速產出不是核心能力問題，而是流程斷層問題。當需求不清、沒有回饋機制、架構逐步腐化時，越快寫越快壞。

「幫我做一個會員系統」很快就能交出結果，但如果沒有領域語言、規格與回饋迴路，後面常常要重做。Skills 的核心價值是把工程師最擅長的流程節點，補回給 AI。

  • 先釐清「要解決什麼」，再做「怎麼做」 決策優先於實作
  • 用可驗證輸出替代憑感覺修補 每步都留下可追溯結果
  • 把架構與維運納入日常節奏 而非交付後才補

slide 04 / 13 mattpocock/skills 的定位這套到底是什麼 不是 Agent 框架不是黑箱平台

它不是「接管整個開發流程」的大框架，也不是 runtime。

它用可組合的 SKILL.md 流程組成工程節點。你可主動啟用，也可由模型依上下文決定觸發。 一份指令不綁死你，重點是「把可複製決策規則」留下來。

  • User-invoked：由你直接叫起，像 /grill-me 或 /to-spec 你主動啟用的流程指令
  • Model-invoked：可由模型依情境啟用，像 tdd、diagnosing-bugs 由模型在情境中呼叫的執行節點
  • 透明且可擴充，核心是「流程可看見」 每步驟有可回看紀錄
# Claude Code：受管理、唯讀、自動更新 $ claude plugins install mattpocock-skills # Codex / 其他 Agent：可編輯副本 $ npx skills@latest add mattpocock/skills $ /setup-matt-pocock-skills tracker / docs path / triage labels（若有安裝 triage） # 兩種安裝方式擇一，避免 skill 重複 ready-to-run

重點：不是一次裝完就萬事大吉，setup 決定後續技能引用範圍。

slide 08 / 13 技能地圖與角色對應常用 skill 一覽 按場景選用不是全都要開
  • /setup-matt-pocock-skills：初始化 tracker、標籤、文件路徑 每個 repo 只要先跑一次
  • /grill-with-docs：先問再做，建立需求上下文 需求訪談 + 領域語言
  • /to-spec：整理完整規格與 AC 把討論轉成可執行文件
  • /to-tickets：縱向切片成可獨立執行的 ticket 避免一次改太多，先跑可驗證路徑
  • prototype：設計不確定點先驗證 UI 路徑先試再定
  • tdd：行為先行，先寫會失敗測試 紅→綠→重構
  • diagnosing-bugs：有系統地抓 bug 根因與回歸 Reproduce/Minimise/Hypothesise/Instrument/Fix
  • code-review：雙軸審查（Standards + Spec） 品質不靠憑感覺
  • /implement：依 spec / tickets 實作並設品質關卡 在約定邊界驅動 tdd，提交前跑 code-review
  • /improve-codebase-architecture：定期治理架構債 找淺模組向深模組演進
slide 09 / 13 先對齊，後定義先釐清，再形成規格 /grill-with-docs → /to-spec先問，後寫

第一個實戰關鍵是先用 /grill-with-docs 把隱藏前提梳理出來：資料來源、狀態名詞、失敗定義、通知方式。

接著 /to-spec 不再做訪談，而是把共識整理成正式規格：目標、角色、In Scope / Out of Scope、Acceptance Criteria、風險與待決議。

slide 10 / 13 任務切片與原型驗證切到可執行，再快跑實驗 /to-tickets · prototype不要一次做完

/to-tickets 把規格拆成 tracer-bullet tickets：每張票交付一條窄而可驗收的端到端行為，並明確標示 blocking edges。

只有當工作大到超過單一 session 才用 /wayfinder：先解開 decision tickets，清圖後通常回到 /to-spec，而不是直接實作。

  • 水平切片容易卡住，因為沒有可交付結果 只完成 schema 或 API，仍看不到使用者行為
  • prototype 用來驗證介面、流程或狀態假設 以單一可分享 HTML 保留可運行證據
  • 每個 ticket 先小步、可撤銷、可回頭 控制變更成本
# /to-tickets sample $ /to-tickets Ticket #1 CSV 匯入 → 今日清單可見 Ticket #2 篩選 → 可驗收的使用者路徑 blocking edges 已標示 # 僅限超過單一 session 的大型工作 $ /wayfinder decision tickets → 通常回到 /to-spec $ prototype 單一可分享 HTML · 驗證後保留證據
slide 11 / 13 實作與除錯：/implement + diagnosing-bugs從能跑到可證明 交付主線與故障入口兩條路徑，不是固定順序

/implement 依 spec 或 tickets 推進實作：在事先約定的 seam 驅動 TDD，並在提交前以 code-review 收尾。

當 bug 出現，不要「再叫修一次」。用 diagnosing-bugs 建立穩定重現、縮小範圍、提出假設、加觀測、修正，最後補回歸測試。

  • 測試關注「行為」而非「實作細節」 重構不會一次炸掉全部
  • diagnosing-bugs 的固定步驟可複用到複雜回歸 多模組問題也能被拆解
  • 確認根因後再修，最後用回歸測試鎖住行為 避免同一問題重演
$ /implement spec-or-tickets tdd at agreed seams → code-review → commit $ diagnosing-bugs Reproduce · Minimise · Hypothesise · Instrument · Fix root cause identified · regression added
slide 12 / 13 持續品質與架構治理不讓專案越做越難 code-review + improve雙軸檢查
Acode-review 雙軸檢查：規格一致性 + 標準品質SPEC / STANDARDS
B/improve-codebase-architecture 掃描深模組機會；是 survey，不是自動大重構每隔幾天或一批功能後
C/handoff 只在脈絡必須跨工具、目錄、人員或旁支任務時搬移可攜式交接

把架構治理當作附加任務做會來不及；把它放入節奏裡，你才會覺得每次開工時都比較快。

$ slide 13 / 13
結語 · 章程總結

不是多加 幾個指令
而是建立可持續流程。

先導入最痛點的一步即可。先從 /grill-with-docs 或 /tdd 開始，讓團隊先看到「回饋差異」。

Takeaways / 帶走

  • 不要依賴「模型能力」替代「工程流程」 先對齊再實作
  • 先建 CONTEXT 與 ADR，再做 spec 與 tickets 減少長期返工
  • 用 /implement、tdd、diagnosing-bugs、code-review 做品質防線 問題可追蹤、可回歸
  • 定期跑 /improve-codebase-architecture 架構先發芽，才能長大
實作順序建議

第1週：tdd + diagnosing-bugs
第2週：每個新功能加 /grill-with-docs；第3週加入 /to-spec /to-tickets /implement； 第4週起每隔幾天跑一次 /improve-codebase-architecture。
