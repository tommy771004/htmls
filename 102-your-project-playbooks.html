slide 09 / 16 Migrations: how not to die遷移專案的第一條守則 playbooks B · CB、C 共同原則
Before · 過去

The big-bang rewrite.

「停下來重寫,18 個月後一次上線。」 舊系統繼續長新功能,新系統永遠追不上; 上線日變成災難日 —— 多數大改寫專案死在這裡。

▶
After · 現在

The strangler fig.

新舊系統並肩運行,連著同一個資料庫。 一次遷移一個畫面,使用者逐步搬家; 舊系統像被絞殺榕包住的樹,慢慢縮小到消失。

Old and new run side-by-side on the same database — that's what makes one-screen-at-a-time possible.

新舊共用同一個資料庫,才可能一次只換一個畫面。(Martin Fowler: Strangler Fig Application)

slide 10 / 16 Same DB · legacy read-only遷移共同原則 before B and C進入 B、C 前必讀
  • The database is the contract — don't redesign it in phase 1 資料庫不動,它是新舊系統之間的合約
  • Legacy code → legacy\ — read-only reference 舊程式碼複製進 legacy\,唯讀,絕不修改
  • Spec per screen, not per table 以「畫面」為規格單位 —— Lab 03 的引擎換個瞄準點
  • Characterize by comparison — same data, old vs new 同樣資料,新舊行為對照驗證
## Legacy reference - `legacy/` is a READ-ONLY copy of the old app. Never edit anything in it. - `legacy/` = source of truth for business rules; `database/*.sql` = source of truth for data shape. When they disagree, stop and ask me.
Read `.\database\*.sql` (scripted schema-only). Write `spec\db-overview.md`: - tables grouped by business area - declared FKs PLUS implicit ones inferred from column names — mark "implicit, confirm" - flag composite keys, missing PKs, triggers Ask me to confirm before we rely on them.
slide 11 / 16 Playbook B — WebForms → web舊 Web 應用現代化 prompt B1畫面盤點

Lifecycle, ViewState, postbacks — describe the behavior, never port the plumbing.

頁面生命週期、ViewState、postback 沒有現代對應物 —— 描述「行為」,不要翻譯「實作」。

  • Screens map ≈ 1:1 to routes 畫面與路由大致一對一 —— B 比 C 容易的原因
  • You can run the old app and compare with your eyes 舊系統跑得起來,可以並排截圖比對
  • Inventory first, then migrate in confirmed order 先盤點、確認順序:簡單 CRUD 先,共用控制項後
Read the legacy app under `.\legacy\` (WebForms — read-only, never modify). Write `spec\screen-inventory.md`: every .aspx page: | Page | Purpose | DB tables | Shared controls | S/M/L | - infer purpose from markup + code-behind - note master pages and .ascx user controls - list dead pages separately — don't drop silently Then propose a migration order: simple lookup/CRUD first, postback workflows last. Ask me to confirm the order.

之後每個畫面: prompt B2 抽出行為規格(欄位、驗證、每顆按鈕的 SQL、要丟棄的 ViewState 花招)→ 確認 → 產生。

slide 12 / 16 The per-screen loop逐畫面循環 —— B、C 的日常 one screen at a time一次一個畫面
01 Pick the next screen from the confirmed inventory order 照確認過的順序挑下一個畫面 INVENTORY
02 Extract the spec — prompt B2 / C1 → spec\screens\{screen}.md 從舊畫面抽出行為規格 SPEC
03 Confirm — you read it; A) build · B) edit the spec 人工確認 —— 引擎的把關點 GATE
04 Build backend → frontend → tests 產生:後端 → 前端 → 測試 BUILD
05 Compare old vs new on the same DB — screenshots or row snapshots 新舊對照:截圖或資料列快照 VERIFY
06 Commit — one screen, one commit 一個畫面一個 commit SHIP
07 /clear — fresh context, next screen 清空 context,下一個畫面 REPEAT
slide 13 / 16 Playbook C — WinForms (VB) → web桌面應用轉 Web prompt C1兩段式抽取

No HTTP layer. Logic lives in event handlers. Claude reads VB fine — just say so in the prompt.

沒有 HTTP 層 —— 你要引入這個系統的第一個 API。 商業邏輯藏在 Button_Click、CellValueChanged 裡;VB.NET 或 VB6, Claude 都讀得懂,在 prompt 裡說清楚就好。

  • UI is a paradigm shift — redesign, don't translate 桌面 UI 要重新設計,不是逐一翻譯
  • Characterize via DB row snapshots — no old UI to diff 用資料列快照對照 —— 沒有舊網頁可以截圖
  • Split: rules to keep vs mechanics to discard 拆開:該保留的規則 vs 該丟棄的桌面機制
Read `.\legacy\{Form}.vb` + `{Form}.Designer.vb` (VB.NET WinForms — read-only reference). Write `spec\screens\{form}.md` in two parts: 1. RULES TO KEEP (the real spec): - business rules in the event handlers - validation — incl. MsgBox checks → field rules - every SQL / stored-proc + its trigger action 2. DESKTOP MECHANICS TO DISCARD: - dialogs, grid cell events, timers, MDI Then propose the web equivalent per the desktop→web mapping table. Wait for my confirmation before building.
